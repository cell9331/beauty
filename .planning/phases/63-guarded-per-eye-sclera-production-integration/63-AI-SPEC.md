# AI-SPEC — Phase 63: Guarded Per-Eye Sclera Production Integration

> AI design contract generated by `$gsd-ai-integration-phase`. Consumed by
> planning and evaluation. This phase uses existing on-device Apple Vision
> observations; it adds no generative model, agent framework, network service,
> or new learned resource.

---

## 1. System Classification

**System Type:** Hybrid — deterministic on-device vision-assisted image pipeline

**Description:**
An SDK integrator supplies a still image and a bounded
`scleraRednessReduction` scalar. The existing native Apple Vision request maps
left/right eye contours and pupils into the one canonical image. Deterministic
Swift code then validates each eye, builds protected hard envelopes, scores
measured redness, derives source-only bounded targets, and composes zero-to-two
per-eye units. Good behavior changes only safe red sclera pixels, preserves
detail and luminance, and abstains locally whenever support is uncertain.

**Critical Failure Modes:**

1. Iris, pupil, highlight, lash, skin, or aperture-exterior pixels are claimed
   or changed.
2. Missing or malformed support is guessed, mirrored, cached, or borrowed from
   the peer eye or another request.
3. Blur/feather expands a score beyond the pre-score hard envelope.
4. The transform globally desaturates/whitens the eye or destroys vessel/detail
   variation instead of reducing measured red excess.
5. Sclera work triggers a second Vision request, leaks sensitive support, or
   changes teeth, pixel-buffer, Demo, or unrelated-effect behavior.

## 1b. Domain Context

**Industry Vertical:** On-device portrait imaging and cosmetic photo retouching

**User Population:** SDK integrators processing user-selected portraits locally

**Stakes Level:** High for privacy and anatomical containment; medium for visual quality

**Output Consequence:** The processed still image may be saved or displayed by
a host app. A containment failure can visibly alter the iris/pupil or expose
sensitive eye-derived support; an overly aggressive correction can look
porcelain, erase vessels, or change identity cues.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
| --- | --- | --- | --- | --- |
| Anatomical containment | Every changed pixel belongs to safe sclera; iris, pupil, highlights, lashes, skin and exterior stay exact | Any protected pixel changes or protection relies on native dark iris color | Critical | SCLERA-10/11 and validated spike guard ordering |
| Per-eye independence | One unsafe eye abstains while a safe peer remains active | Peer support is mirrored/reused or one rejection disables both eyes | High | SCLERA-09/13 |
| Redness reduction | Material positive red excess decreases monotonically within bounded channel movement | Global whitening/desaturation or unrelated pixels change | High | SCLERA-12 |
| Natural detail | Vessel/detail variation, shading, edges, alpha and luminance remain natural | Porcelain fill, blurred texture, clipped highlights or structural change | High | Frozen Phase 62 review criteria |
| Negative stability | Normal/low-redness eye abstains or remains visually natural at maximum intent | Normal sclera is visibly recolored or brightened | High | Authorized negative contract |
| Privacy | Only fixed aggregate counts/outcomes leave request-local code | Coordinates, pupils, masks, colors, paths, pixels or vein-like descriptors persist | Critical | EVID-09 and SCLERA privacy constraints |

### Known Failure Modes in This Domain

- A dark native iris can hide an unsafe geometric mask because the downstream
  redness score returns zero there.
- Vision pupil landmarks may be missing or inaccurate during blink, closure,
  glare, occlusion, gaze, glasses, or contacts.
- Blurring a correctly clipped score can reintroduce nonzero weights across the
  iris or aperture boundary unless the hard envelope is applied again.
- An eye aperture is not equivalent to sclera; it also contains iris, pupil,
  highlights, lash margins, and potentially occluded regions.
- Broad red-channel suppression can affect skin, makeup, iris, vessels, and
  natural shading while still appearing numerically less red.

### Regulatory / Compliance Context

- Local-only processing and data minimization are mandatory repository
  contracts. Eye geometry, pupils, masks, candidate colors, vein-like detail,
  fixture locators, rights records, and reviewer identity are never public,
  Codable, persisted, logged, networked, or tracked.
- Rights-approved internal evaluation applies only to the selected ignored
  fixtures and does not establish commercial, biometric, population, shipping,
  or release approval.
- No medical diagnosis or treatment claim is made; this is cosmetic image
  processing.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
| --- | --- |
| Image-quality reviewer | Original-detail naturalness, vessel/detail, luminance, and negative-stability judgment |
| SDK safety reviewer | Anatomical containment, per-eye failure isolation, privacy and API-boundary verification |
| Test maintainer | Deterministic scenario construction, aggregate oracle checks and regression ownership |

## 2. Framework Decision

**Selected Framework:** Native Apple Vision via the existing `VisionFaceDetector`

**Version:** System `Vision` framework on the package's iOS 17 / macOS 14 minimums

**Rationale:**
The repository already performs one `VNDetectFaceLandmarksRequest`, maps actual
left/right eye contours and pupils into request-local image-normalized values,
and carries explicit anatomical-order metadata. Phase 63 needs deterministic
guarding and color correction around those observations, not another model or
an agent/RAG framework. Reusing the existing request preserves privacy,
dependency direction, latency ownership, and the one-canonical-request
contract.

**Alternatives Considered:**

| Framework | Ruled Out Because |
| --- | --- |
| New Core ML segmentation model | No approved dataset/checkpoint/conversion/redistribution chain; adds resource, privacy and performance scope |
| External beauty SDK or cloud vision API | Violates local-only, no-network, no-new-dependency and independent-evidence boundaries |
| Face-box/eye-geometry proxy | Cannot establish actual per-eye contour/pupil ownership and would guess protected anatomy |
| LLM/agent frameworks | No language generation, retrieval, tools, prompts, or agent state exists in this deterministic image pipeline |

**Vendor Lock-In Accepted:** Partial — existing Apple Vision dependency is
accepted for Apple-platform SDK targets; no additional provider lock-in is
introduced.

### Entry Point Pattern

```swift
let route = resolveStillImageGeometry(
    image: canonical.ciImage,
    metadata: canonical.metadata,
    imageExtent: CGSize(width: canonical.width, height: canonical.height),
    parameters: parameters,
    requiresLocalSupport: true
)
let context = BeautyStillImageRequestContext(
    canonicalImage: canonical,
    selectedFaceObservation: route.selectedFaceObservation
)
let owner = BeautyLocalRetouchCompositionOwner(source: canonical)
let result = BeautyScleraRednessProvider.makeResult(
    source: canonical,
    eyeSupport: context.selectedFaceObservation?.observedEyeSupport,
    observedOrder: context.selectedFaceObservation?.observedEyeOrder,
    strength: parameters.scleraRednessReduction,
    owner: owner
)
let composed = try owner.compose(result?.units ?? [])
```

### Key Abstractions

| Concept | What It Is | When You Use It |
| --- | --- | --- |
| `VNDetectFaceLandmarksRequest` | Existing one-shot native landmark detector | Once per admitted still-image request |
| `BeautyObservedEyeSupport` | Package-only mapped side/contour/pupil evidence | Validate each eye independently |
| `BeautyObservedEyeOrder` | Explicit anatomical side-order verdict | Fail closed when side ownership is ambiguous |
| `BeautyCanonicalStillImage` | Checked opaque sRGB RGBA8 immutable source | Every mask score and target reads from it |
| `BeautyLocalRetouchCompositionOwner` | Source-binding, Q16 blend and collision authority | Issue and compose per-eye units exactly once |

### Common Pitfalls

1. Vision landmark points are face-local before mapping; never reinterpret them
   as image-normalized or apply orientation a second time.
2. Pupil absence/inaccuracy during blink or occlusion must cause local
   abstention, not center estimation or peer-eye mirroring.
3. A pre-blur clip is not final containment; multiply by the same hard envelope
   after every blur or feather.
4. Native iris color is not a safety oracle; Phase 64 must open the redness gate
   geometrically and recolor protected iris pixels adversarially.

## 4. Implementation Guidance

**Model Configuration:** There is no configurable learned model. Use the
system Vision revision already owned by `VisionFaceDetector`; do not add a
second request or revision override in this phase. Provider thresholds are
deterministic constants frozen through the declared private and perturbation
calibration sweep.

**Core Pattern:** Validate side ownership, then validate and rasterize each eye
independently. Build `hardEnvelope = insetAperture - iris/pupil - highlights -
lashMargin` before scoring. Compute source-only sclera likelihood and positive
red excess inside that envelope, feather locally, re-clip, derive a bounded
source-only target, and issue one unit per accepted eye. Any uncertainty returns
no unit for that eye.

**Tool Use:** XCTest, the existing fixed-output ignored-fixture runner, Phase 62
private bundle discovery, JSON/privacy scanners, and the current composition
owner. No model download, network API, analytics, server, or new dependency.

**State Management:** All support, masks, exclusions, scores, proposals, and
summaries are stack/request-local immutable values. No cache or retained
provider state. Diagnostics contain fixed aggregate counts/outcomes only.

**Context Window Strategy:** N/A — no language model or prompt context. Image
work is bounded by validated canonical dimensions and per-eye ROIs.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

Production Swift does not use Pydantic. The only permissible Python mirror is
an offline validator for fixed aggregate evaluation output; extra fields are
forbidden and raw support cannot be represented.

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class ScleraEvalAggregate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    status: Literal["pass", "fail"]
    fixture_count: int = Field(ge=2, le=2)
    eye_scenarios: int = Field(ge=0)
    accepted_eyes: int = Field(ge=0)
    protected_changed_pixels: Literal[0]
    outside_mask_changed_pixels: Literal[0]
```

Validation failure stops the private child and emits only a fixed error code;
there is no retry that broadens schema or support.

### Async-First Design

Independent engine requests may execute concurrently, but each request owns
its canonical source, observations, owner, units, and aggregates. Do not use a
shared mutable provider or cache. No streaming behavior exists.

### Prompt Engineering Discipline

N/A — no prompts or generated language. The equivalent discipline is frozen
deterministic criteria: thresholds and pass rules are fixed before outcome
inspection, and failed cases cannot trigger ad-hoc relaxation.

### Context Window Management

N/A — no language-model context. Limit memory by rasterizing bounded eye ROIs,
not whole-frame float masks, and release all temporary arrays with the request.

### Cost and Latency Budget

There is no per-call network cost. Phase 63 may record aggregate local timing
for regression only, but it makes no target-device budget or performance claim.
The hard invariant is one existing Vision request; a second detection is a
failure regardless of measured speed.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric | Measurement Approach | Priority |
| --- | --- | --- | --- |
| Actual support ownership | Exactly one canonical request; only current mapped canonical-order side/contour/pupil support is consumed | Code | Critical |
| Protected containment | Zero claims/changes in iris, pupil, highlights, lashes, skin or aperture exterior; zero outside-mask changes | Code; Phase 64 adversarial extension | Critical |
| Post-filter containment | Every nonzero feathered weight remains inside the identical hard envelope | Code | Critical |
| Per-eye isolation | Rejected left/right eye yields no unit for that side while accepted peer behavior is unchanged | Code | Critical |
| Red-excess improvement | Positive accepted pixels reduce material red excess monotonically within channel/luminance bounds | Code + private aggregate | High |
| Natural detail and negative stability | Detail/texture, shading, alpha and normal-sclera appearance remain natural | Code + Human original-detail review in Phase 64 | High |

### Reference Dataset

**Size:** Two independently authorized genuine originals (one visible-redness
positive, one normal/low-redness negative), expanded into at least 20 fixed

## 6. Guardrails

### Online (Per Request)

| Guardrail | Trigger | Intervention |
| --- | --- | --- |
| Side ownership | Missing/invalid anatomical order or duplicate side | Abstain from ambiguous sclera work |
| Eye support | Missing/multiple/outside pupil; malformed/collapsed contour | Drop only affected eye |
| Protected envelope | Empty or implausible envelope after iris/highlight/lash exclusions | Drop only affected eye |
| Transform safety | No material red excess or bounded target cannot be formed | Emit no proposal for pixel/eye |
| Composition ownership | Source mismatch, invalid unit, duplicate token or pixel collision | Reject unit/claim and preserve source |
| Scope boundary | Pixel-buffer/reset/Demo/alias/Testing-only demand | Do not invoke production sclera provider |

### Offline (Local Evaluation Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
| --- | --- | --- |
| Protected/outside changed pixels | Every deterministic and authorized run | Block phase on any nonzero value |
| Accepted/rejected/fail-closed eyes | Every fixed support scenario | Investigate; never recover coverage by guessing |
| Positive red-excess delta | Authorized positive, each accepted eye | Block if no bounded improvement |
| Negative output/naturalness | Authorized negative at maximum intent | Block on visible/material instability |
| Detail/luminance/channel bounds | Every accepted real and mechanics output | Block or tighten transform |
| Privacy schema | Every tracked/staged change and private child run | Block on any sensitive field or raw error |

## 7. Production Monitoring

**Tracing Tool:** Existing local aggregate observations only; no Phoenix,
network tracing, analytics, image persistence, or request sampling is added.

**Key Metrics to Track:** In development/private verification only: provider
invocations, accepted/rejected eye counts, proposal/changed pixel counts,
collision count, protected/outside changed counts, and fixed phase status.

**Alert Thresholds:** Any protected/outside change, source mismatch, stale-
support retention, second Vision request, malformed schema, or privacy finding
is blocking. Coverage reductions are reviewed but never repaired by weakening
an anatomical guard.

**Smart Sampling Strategy:** No production sampling in this milestone. Local
evaluation runs every authorized fixture and every fixed adversarial/failure
scenario. Future population/device monitoring requires a separate privacy and
retention design.
