# Phase 65: Combined Facade, Privacy, and Milestone Closeout - Context

**Gathered:** 2026-08-08
**Status:** Ready for planning
**Mode:** Autonomous recommendations accepted under the active `--auto` run

<domain>
## Phase Boundary

Prove that the independently admitted and promoted teeth and sclera slices can
run together through the public still-image facade without shared authority,
order dependence, stale state, privacy expansion or false product scope. Close
v1.15 only after focused, private, full-regression, owner, independent phase-
verification and separate milestone-audit gates agree. This phase adds no new
product effect, public parameter, preset, Demo control, realtime route, model,
network behavior or visual tuning.

</domain>

<decisions>
## Implementation Decisions

### Combined public-facade oracle

- **D-01:** Exercise both existing public entries, `process` and
  `processResult`, with `teethWhitening: 1` and
  `scleraRednessReduction: 1`; Testing may inject only deterministic current-
  request support and may never create admission.
- **D-02:** Keep renderer inventory exactly 74. The two standalone renderer
  cases remain separate evidence owners; combined behavior is a public-facade
  XCTest, not a third product-output case.
- **D-03:** Run source, teeth-only, sclera-only and combined requests from fresh
  independent harnesses over the same deterministic RGBA input and current
  support. The test must observe one canonical request and one composition.
- **D-04:** Build the expected combined bytes from an independent per-pixel
  merge of the two standalone outputs: one changed standalone owns the pixel,
  neither preserves source, and two changed standalones preserve source as a
  collision. Do not call a production merge helper to construct the oracle.
- **D-05:** Require exact dimensions, orientation, opaque alpha and explicit
  sRGB. Combined output must retain unrelated eligible color work and typed
  payload-free failures.
- **D-06:** Retain the feature-neutral Phase 55 collision matrix as the explicit
  cross-provider collision oracle. Real teeth/sclera anatomy should be
  disjoint; an injected conceptual collision must preserve source locally and
  retain all noncolliding sibling pixels independent of unit order.

### Failure and lifecycle isolation

- **D-07:** Cover injected teeth failure, whole-sclera failure, left-eye
  failure and right-eye failure separately. Every unaffected provider/unit and
  unrelated eligible effect continues byte-exactly.
- **D-08:** A minimal Testing-only support fixture may provide valid paired eye
  support without lip support to prove teeth failure. It remains SPI-only,
  aggregate-only and cannot affect production admission or output.
- **D-09:** Missing/no-face, malformed current support and invalid eye order
  abstain from only their owned work. No synthetic, mirrored, peer or previous-
  request repair is allowed.
- **D-10:** Valid-invalid-valid, repeated combined calls, a thrown middle call,
  independent parallel engines, reset and pixel-buffer routes prove no retained
  support, masks, proposals, pixels or summaries.
- **D-11:** Cooperative cancellation remains publication-discard semantics from
  the existing request-local foundation. Synchronous provider work gains no
  hidden global cancellation state.
- **D-12:** Public/SPI diagnostics remain fixed aggregates only. Reflection,
  descriptions and errors expose no anatomy, indices, colors, paths, fixtures
  or owner identities.

### Compatibility and privacy

- **D-13:** Compatibility remains exactly 61 stored/CodingKey/initializer
  fields, five byte-stable neutral presets, 74 renderer cases and three disabled
  nil-mapped local-retouch Demo rows.
- **D-14:** Admission remains exact `0/1/1/2` for none/teeth/sclera/both. A
  combined request uses one canonicalizer, one Vision mapping, one request
  context, both independent providers and one composition owner.
- **D-15:** Missing legacy keys stay zero; aliases, global color, geometry,
  Testing names, Demo labels and `去脂` cannot activate either provider.
- **D-16:** Raw landmarks, lip/teeth geometry, pupils, masks, candidate colors,
  vein-like detail, image bytes, paths and reviewer identity remain request-
  local/package-private and absent from public/SPI/Codable/persistence/log/
  metric/network/tracked surfaces.
- **D-17:** Private teeth and sclera evidence/output runners remain independent,
  ignored and fixed-output. Each must rerun; neither pair supplies sibling or
  combined naturalness credit.
- **D-18:** Complete source/resource/network scans are fail closed. No remote
  URL/session, external model, bundled unapproved binary or tracked review media
  may appear.

### Product, verification and lifecycle

- **D-19:** Product owners remain exactly `白牙 = implemented`,
  `祛红血丝 = implemented`, `嘴唇 = implemented`, `眼睛 = partial`, and
  `去脂 = future`. Phase 65 performs owner equality, not another promotion.
- **D-20:** `去脂` aliases and proxies include upper-eyelid fullness/fat/
  defatting plus eye-height/lift/brow/warp/smoothing/eye-bag/dark-circle
  relations across production, Testing, renderer, preset, Demo and docs.
- **D-21:** All eight HIGH owners must pass mutation self-tests and isolated
  live modes. Missing, skipped, unclassified or scanner-child failure blocks
  closeout.
- **D-22:** Required final execution includes both standalone private 6/6
  matrices, both private actual-Vision provider pairs, every repository opt-in
  Vision integration test, focused combined/adversarial/provider/composition
  suites, full SwiftPM and explicit Demo build/test.
- **D-23:** Perform a scoped code review and fix/recheck before canonical phase
  verification. Do not silently accept HIGH findings or weaken prior bounds.
- **D-24:** Phase verification owns the implemented state; a separate
  `gsd-audit-milestone` pass owns 40/40 traceability, cross-phase integration and
  end-to-end intent before OUT-09 closes.
- **D-25:** The milestone audit may authorize completion readiness only. It does
  not archive, tag, clean up, ship or claim release readiness; those require
  separate user-directed lifecycle commands.
- **D-26:** Durable closeout stores only aggregate counts, fixed dispositions
  and bounded nonclaims. No visual rerun or effect tuning is required because
  both standalone slices already passed fresh original-detail review.
