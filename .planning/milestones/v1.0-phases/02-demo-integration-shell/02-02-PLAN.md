# Plan 02-02: Build Editor Category, Subcategory, Slider, and Disabled-State View Models

<objective>
Create the value-driven Demo state model that makes Phase 2 category visibility, disabled availability, display ranges, SDK normalization, status copy, and reset behavior directly testable before SwiftUI rendering is completed.
</objective>

<user_story>
As an integration tester, I want the editor taxonomy and parameter values represented as deterministic Swift state, so that category coverage and `BeautyParameters` normalization can be verified without brittle UI automation.
</user_story>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| Visible labels drift from roadmap requirements | high | Store visible labels in descriptors and assert exact ordering in tests. |
| Filters become active because SDK filter fields already exist | high | Mark Filters and filter rows disabled in descriptors and assert `Coming in Phase 5`. |
| UI display values bypass SDK normalization | high | Centralize conversion in `BeautyParameterStore` and test `0...100` plus `-100...100` ranges. |
| Disabled controls trigger unavailable resource or media behavior | medium | Availability values contain reason/badge only and no executable resource/media action. |
| Reset behavior mutates unrelated controls | medium | Add tests for single reset and reset-all snapshot restoration. |
</threat_model>

## Artifacts this phase produces

- `BeautyCategoryModels.swift` with top-level categories, facial-feature subcategories, and availability states
- `BeautyControlDescriptor.swift` with stable control IDs, visible labels, display ranges, and optional SDK parameter keys
- `BeautyParameterStore.swift` with display values, normalized `BeautyParameters`, applied/pending status, single reset, and reset-all
- XCTest coverage for `DEMO-02`, `DEMO-03`, `DEMO-04`, `DEMO-05`, and `DEMO-08`
