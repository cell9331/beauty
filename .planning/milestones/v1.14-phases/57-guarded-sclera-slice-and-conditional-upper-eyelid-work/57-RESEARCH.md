### Pattern 1: Two independent projections, one authority

Parse the full Phase 54 document structurally, select each feature by exact identity, require uniqueness, exact key sets, exact reason order/set, five zeros, empty reviews, and matching aggregate rows. Never copy a row into a mutable Phase 57 status JSON that could become a second authority. [VERIFIED: Phase 54 ledger shape and Phase 56 `decision_failures()`]

### Pattern 2: Production is a read-only fixture

Plans may add tests, checker, inventory, evidence, and owner closeout text. They must not repair an unexpected SDK/Demo drift by adding either feature; a discovered active route is a blocking failure. [VERIFIED: `57-CONTEXT.md` D-57-09]

### Pattern 3: Whole-source semantic boundary

Derive every production path from `BeautySDK/Sources/**/*.swift` at runtime. Apply identifier/content classifiers to all files, including files created after the checker was authored. Use explicit allowlists only for shipped neutral mechanics such as the feature-neutral composition core; candidate or synonym identifiers have no production allowlist while the gates are closed. [VERIFIED: Phase 56 post-verification repair `8cf422f` described in `56-REVIEW-FIX.md` and `56-VERIFICATION.md`]

### Pattern 4: Proxy relation, not proxy-token ban

LID-04 must reject a relation between an eyelid-fullness concept and a shipped proxy. Existing `eyeHeight`, `upperEyelidLift`, `eyebrowYPosition`, `skinSmoothing`, and eye-warp code are valid by themselves. Fail only when a candidate/synonym is assigned from, forwarded to, routed through, renamed to, described as, or asserted equivalent to one of those proxies. Dark-circle and eye-bag tokens have no current production owner and should be rejected if introduced as eyelid-fullness substitutes. [VERIFIED: current production sources and `57-CONTEXT.md` D-57-08/D-57-17]

### Pattern 5: Same live path for clean and mutated fixtures

`configure_root(root)` must derive every path and complete production source tree from the supplied root. Self-tests copy actual fixtures, mutate one anchored fact, invoke the same `classified_live_failures()` used in normal mode, require stable rule IDs, and restore the original root in `finally`. A missing mutation anchor is itself a test failure. [VERIFIED: Phase 56 checker lines 95-133, 637-818, 925-962]

### Anti-Patterns to Avoid

- **Broad `eye`, `redness`, `lid`, `fat`, or Chinese-title bans:** these create false positives in legitimate tests/docs/taxonomy and can erase shipped features.
- **Selected-file candidate scan:** a neutrally named new provider or transform can bypass it.
- **Counts as security evidence:** `111/111` is useful reporting but named HIGH identities and per-threat executable mutations are the authority.
- **Mechanics-to-product inference:** Phase 55 composition and spike oracles do not open either feature gate.
- **Absence-as-classifier claim:** no implementation means SCLERA-02..05, LID-03, and LID-05 are not applicable, not proven algorithms.
- **Evidence lifecycle before gates:** final evidence/frontmatter and root owner promotion must remain pending until the final-only commands pass.

## Whole-Source Neutral-File Mutation Strategy

1. Copy only required real fixtures into a temporary repository-shaped root: full `BeautySDK/Sources`, focused SDK tests, Demo source/tests, Phase 54 decisions, Phase 57 threat/evidence fixtures, product owners, and both blueprint ledgers.
2. Recompute `PRODUCTION_SWIFT_FILES` with a recursive glob from the configured root for every invocation; never cache the original repository list.
3. Establish a clean baseline through the normal live classifier.
4. Add new files with neutral names such as `LocalColorProvider.swift`, `LocalToneProvider.swift`, or `RequestTransform.swift`; never give the filename a candidate clue.
5. Insert one canonical/synonym route per case. Require the candidate-specific rule and, for alias/coupling cases, the semantic alias/proxy rule too.
6. Exercise at least one new-file mutation for every candidate synonym family and every proxy family, not just one representative per feature.

## Common Pitfalls

### Pitfall 1: Treating the roadmap's positive wording as current authorization
**What goes wrong:** A planner implements sclera mechanics because the phase goal says “qualify.”
**How to avoid:** Resolve the conditional through the current immutable closed rows before planning tasks.
**Warning sign:** Any planned SDK production file modification or image-effect test.

### Pitfall 2: Marking LID-04 not applicable
**What goes wrong:** The closed gate is used to skip active proxy rejection.
**How to avoid:** Keep LID-04 affirmative with source relation tests and neutral-file mutations.
**Warning sign:** No mutation couples `upperEyelidFullnessReduction` to `upperEyelidLift` or `skinSmoothing`.

### Pitfall 3: Banning shipped proxy names
**What goes wrong:** The checker fails on legitimate `eyeHeight`, `upperEyelidLift`, eyebrow motion, and smoothing implementations.
**How to avoid:** Match candidate/proxy relationships, not proxy tokens alone; add clean proxy-only disconfirmation cases.
**Warning sign:** Current production source fails before any mutation.

### Pitfall 4: Selected-file synonym coverage
**What goes wrong:** A neutral new provider file bypasses the checker.
**How to avoid:** Recursively scan all `BeautySDK/Sources/**/*.swift` content on every configured root.
**Warning sign:** Mutation filenames contain the feature name or only known integration owners are copied.

### Pitfall 5: Removing honest disabled taxonomy
**What goes wrong:** Broad absence logic deletes `去脂`/`祛红血丝` from the Demo or ledgers.
**How to avoid:** Require exact allowed occurrences and exact disabled/future states.
**Warning sign:** Repository-wide substring bans on Chinese titles.

### Pitfall 6: Overclaiming spike safety
**What goes wrong:** Guarded mechanics are described as qualified sclera output, or tone/frequency mechanics as a qualified eyelid method.
**How to avoid:** SCLERA-02..05 and LID-03/LID-05 remain `not_applicable_closed_gate`; cite spike results only as reasons not to hand-roll a future implementation.
**Warning sign:** Words such as implemented, effective, natural, or production-ready in finalized Phase 57 evidence.

### Pitfall 7: Evidence report becomes a second decision source
**What goes wrong:** A Phase 57 status table can diverge from Phase 54.
**How to avoid:** Label the report a read-only projection, require exact upstream identity and values, and reject independent eligibility fields.
**Warning sign:** Phase 57 invents `eligible`, `approved`, or review inputs.

### Pitfall 8: Running human/browser/image review
**What goes wrong:** Missing evidence is treated as a user checkpoint and repeated Phase 54 reviewer mechanics are mistaken for effect evidence.
**How to avoid:** Keep all validation automated; no file selection or visual UAT is required.
**Warning sign:** A plan contains `checkpoint:human-verify`, browser navigation, or before/mask/after output.
